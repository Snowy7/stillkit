Turning mypaper-ui into its own cross-platform library

Plan · 2026-11-07 · repo: desktop-wallpaper, crates/ui

What: move crates/ui into its own repo, keep mypaper building from it, then grow it into a general UI library: a declarative element tree, a shared animation runtime, one component set, and backends for Windows, macOS and Linux.

Recommendation: keep our strongest property as a rule on every OS: no GPU device in the process, and nothing drawn when nothing changes. That is why our bar idles at 8.5 MB and 0 wakes, while Rune's hello app measured 159 MB and loaded the NVIDIA driver on this PC. The element tree compiles down to today's DisplayList, so damage-only redraw and existing code keep working throughout.

Decided (v2): the library is stillkit, in Snowy7/stillkit, private until 0.1. Linux work runs on m6u. mypaper's main stays untouched for now: the switch-over lives on a separate branch. Still open: the renderer for macOS and Linux, decided from the phase 2 spikes.

Where it stands today

ConfirmedFrom the code at ac8f1c6a:

  • Already self-contained. crates/ui/Cargo.toml depends on no other mypaper crate: just windows, AccessKit, log, anyhow and png. 31 modules, about 17.5k lines plus vendored accesskit_windows, 107 commits of history.
  • Few mypaper references. About 20: the window class names (mypaper.ui, mypaper.ui.app), the MYPAPER_BLESS golden variable, the engine glass window class looked up in surface.rs, Studio's monochrome tokens in controls.rs, and comments.
  • Glass is already a hook. glass.rs only says where glass goes and tells a Backdrop (the shell's engine client). The engine side can stay in mypaper.
  • Three users. shell (526 use sites: icons, theme, glass, menu, layout, golden), Studio (433, of which 105 are controls), files (24).
  • What keeps it from being a library:
    • Two component sets: kit.rs (Frame, used by shell surfaces) and controls.rs (Builder, used by Studio), each with its own ButtonKind, Align and Palette.
    • An older token API (Tokens, Colors, Ink, Step) kept beside Theme.
    • Layout by hand-sliced rects.
    • Animation wired separately in each component.
    • Everything is Win32.

Target architecture

Five layers. Apps normally write only the top one; the DisplayList stays public so custom controls, charts and today's code can still draw directly.

Key choices

What writing UI looks like

Today (shortened)
let mut f = Frame::new(&mut ui.text, &theme, s, &ix);
let (title, rest) = body.take_top(f.line(TextRole::Title2), f.px(8.0));
f.label(title.x, title.y, "Sound", TextRole::Title2,
        theme.color.label, title.w);
let (row, rest) = rest.take_top(f.px(theme.metrics.control), f.px(8.0));
f.slider(VOLUME, row, m.level, "Volume", Some(Icon::Volume(2)));
let (row, _) = rest.take_top(f.px(theme.metrics.item), 0.0);
f.switch(MUTE, row.right(), row.center_y(), m.muted, "Mute", true);
// …and the input loop maps VOLUME / MUTE hits back to the model
Proposed
fn view(s: &Sound, cx: &mut Cx<Sound>) -> El<Sound> {
    col().gap_token(Gap::Block).pad_token(Pad::Panel).surface()
        .child(text("Sound").role(TextRole::Title2))
        .child(Slider::new("volume", s.level)
            .icon(Icon::Volume(2))
            .on_change(|s, v| s.level = v))
        .child(Switch::new("mute", s.muted).label("Mute")
            .on_toggle(|s| s.muted = !s.muted))
}

Keys ("volume") name elements for diffing, animation, accessibility ids and scripts. Lengths come from theme tokens, so styles keep working unchanged.

Looks and materials

Liquid, One UI, Solid, Fluent and Mono become data the library ships, not a closed Style enum. Components read only theme values and never ask which look is active.

Today

  • ConfirmedTheme::new(style, scheme, accent) turns a look into values through match arms in theme.rs (lines 296–346, 432–437, 671–697). In the kit, only kit.rs:577 (a Mono case) checks the look by name.
  • Glass: theme::material(style, tint) gives a GlassMaterial, and the engine draws it through the Backdrop hook.
  • GlassMaterial::tuned sets refraction and highlight to 0 unless the look is Liquid (lensed(style)). That rule, not anything technical, is what blocks a lens on other looks.
  • The current look is a process global (theme::active()). The shell checks the look by name 148 times.

A preset is one value of each part. To mix, take parts from different presets, or set any single property yourself. You can mix by place too: set a theme on one subtree.

App::new("Sound").theme(Theme::liquid(Scheme::System, Accent::System))

let t = Theme::one_ui(scheme, accent).material(Material::liquid());  // One UI with Liquid glass
let t = Theme::liquid(scheme, accent)
    .shape(Shape::one_ui())                  // One UI's corners
    .type_ramp(TypeRamp::one_ui())           // One UI's bolder text
    .material(Material::liquid().refraction(0.3).blur(20.0))
    .radius(Radius::Control, 10.0);
let t = Theme::from_file("looks/sunset.toml")?;       // a look as data

col().theme(Theme::mono(..)).child(dock)             // one subtree in another look
tx.set_theme(Theme::one_ui(..))                      // live switch; colours spring across

Every match on the look becomes a theme value: control radius (None = capsules), icon set (Lucide vectors or Segoe Fluent glyphs), stroke weight, focus ring, material. A new look needs no code.

Values derived after mixing

  • Card radius is concentric (surface radius minus pad), so One UI corners with Liquid padding give a new card radius automatically.
  • Text contrast depends on the material. Labels on glass hold 7:1, secondary text 4.5:1, accent 3:1. A clearer material re-checks them and lightens or darkens the steps until they pass.
  • theme.check() reports anything a mix can't fix, such as text that can't reach contrast over a very clear material. The built-in looks pass it in the golden tests.

Who draws the glass

The look says which material a surface wants. A Backdrop provider the app registers draws it, outside our process, so the CPU-only rule holds. Each provider reports what it can do, and looks degrade cleanly: Liquid without a lens provider keeps its tint, shapes, type and motion, frosted instead of refracting.

ProviderDrawsLens
mypaper engine (stays in mypaper)liquid-rust glass in the engine processyes, on any look
macOS built-inNSGlassEffectView on macOS 26+, NSVisualEffectView beforesystem glass only
Windows built-inDWM Acrylic or Mica for app windows. Unchecked whether layered popups can use itno
Linux built-inKDE's blur protocol where the compositor has itno
none (headless, goldens)the look's tinted fillno

The user's material sliders (Knobs, from config.json) become generic MaterialOverrides the app passes in. The theme goes through context instead of the theme::active() global.

Repo and the dev loop

  • New repo, made with git filter-repo on crates/ui so its 107 commits of history come along.
  • Layout: crates/<name> (core and platform backends behind cfg), crates/<name>-kit (components and themes), examples/ (hello, gallery), goldens under tests/golden/<os>/.
  • mypaper depends on it by a pinned git rev. For working on both at once, a local [patch] in .cargo/config.toml points at a sibling checkout (assumed D:\Coding projects\<name>). It is not committed, so CI always builds the pinned rev.
  • A change mypaper needs: commit to the library, then bump the rev in mypaper in the same sitting. Agent briefs on the shared main checkout must say which repo they own.

MeasuredSame Control Center panel, release builds, real GNOME session. Full report: docs/research/linux-spike/report.md in stillkit.

  • No GPU library loaded in any run. No commits and zero CPU ticks in steady idle. Damage was exactly the slider or the label.
  • vello_cpu's stock glyph atlas allocates 64 MiB pages: a CPU cache can rebuild the GPU memory problem. Off, it keeps nearly all its speed.
  • tiny-skia's full draw is dominated by the uncached soft shadow; at 2× it reached only half the frame rate.
  • GNOME has no layer-shell: a real bar or overlay there needs a GNOME Shell extension. KDE and wlroots have wlr-layer-shell. X11 uses dock windows and struts.
  • IME: text-input-v3 in Mutter and KWin, IBus as fallback. Accessibility: AccessKit's AT-SPI adapter. Blur: KDE's blur protocol; newer Mutter has ext-background-effect-v1, not yet on this host.

Render modes and glass (added 2026-11-07)

Liquid Glass is now stillkit's own: crates/stillkit-glass is liquid-rust by al1h3n (MIT OR Apache-2.0, credited), with mypaper's speedups. It already does liquid merging (a smooth signed-distance union per container) and morphs. mypaper never wired those up.

ModeUI drawn byGlassCost
Cpu (default)software renderer, as todaya GPU process that already exists (mypaper's engine, a shared glass host), else noneabout 5–8 MB, no driver
Gpuhardware Direct2D on Windows; vello_hybrid on Linux and macOSstillkit-glass on the same device, in-processabout 150–240 MB of driver memory
AutoNo glass: Cpu. Glass and an existing GPU process to reuse: Cpu with that process. Otherwise Gpu, because a separate process would pay the same driver cost. The rule is confirmed by measurement before it is fixed.

Both modes keep damage-only redraw and zero idle work. Golden tests run on the CPU path; GPU output is checked against it within a small tolerance.

Final acceptance (Islam, 2026-11-07): every combination works with no issues. That means CPU alone, GPU alone, and CPU and GPU together, which is a per-surface choice inside one process. Glass comes from a separate process when one exists, or in-process.

mypaper must not get slower or bigger, and lower is better. It stays in CPU mode, and nothing GPU-related compiles or loads unless a surface asks for it.

Risks

  • Scope. Cross-platform from day one is the biggest risk: IME and accessibility alone are large on each OS. Phases 7 and 8 can slip without blocking mypaper, which only needs Windows.
  • CPU rendering on macOS. We need to confirm that handing CoreGraphics bitmaps to a CALayer keeps our process free of a Metal device and stays smooth on Retina sizes. The spike answers this before any backend work.
  • Text differs per OS, so goldens are per OS and layout can shift a pixel between them. Components must not depend on exact text widths.
  • Two repos on a shared checkout. Agents can commit library changes without bumping mypaper's rev (or the reverse). Briefs name the repo, and a check in mypaper warns when the local patch differs from the pinned rev.
